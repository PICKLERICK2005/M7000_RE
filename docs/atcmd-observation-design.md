# AT Command Boundary — Passive Observation Design (Recon Result)

Date: 2026-08-16. Target: TP-Link M7000(EU) v3.20, firmware 3.0.2 Build 241129 Rel.3n.
Predecessors: [hardware-validation-002.md](hardware-validation-002.md),
[hardware-validation-003.md](hardware-validation-003.md).

**This is a design / recon note, not a hardware validation.** The question asked was
whether the `/tmp/atcmd` transaction generated by one preferred-RAT change can be
physically observed passively, reversibly, and with justification, using access we
already have. **Answer: no.** No sufficiently passive observation channel for
`/tmp/atcmd` exists with current access. No RAT write was performed this session, because
repeating validation 003 without an internal observer would produce no new evidence.

## 1. Static prediction, reverified against the repo

The AP-side translation for the two policies of interest, taken from
[analysis/modem-control-paths.json](../analysis/modem-control-paths.json) (builder-A at
`mobile` VA `0x33220`, template `AT*BAND=<NwMode>`) and corroborated by
[analysis/modem-state-machines.json](../analysis/modem-state-machines.json)
`preferred_rat_policy.conversion_sent`:

| UI policy | `networkPreferredMode` | AT\*BAND NwMode |
| --- | ---: | ---: |
| GSM only (hidden) | 0 | `AT*BAND=0` |
| 3G Only | **1** | **`AT*BAND=1`** |
| 4G Only | 2 | `AT*BAND=5` |
| 4G Preferred | **3** | **`AT*BAND=11`** |
| out of range | — | `AT*BAND=99` |

So the two commands a live observer would expect are `AT*BAND=1` (forward, → 3G Only) and
`AT*BAND=11` (restore, → 4G Preferred). This matches the mapping named in the task.

builder-A is the *supported-inference* live setter: its `(this, value, correlation-ID)`
signature matches how the event handler invokes virtual slot `+0x24`. A second builder-B
at VA `0x3336c` (`AT*BAND=%d,,,,,%d`) exists and is not believed live for this path.

### A prediction worth testing if a channel ever exists

[analysis/modem-state-enums.json](../analysis/modem-state-enums.json) records a known
asymmetry: policy values 0, 2, 3 round-trip through `AT*BAND` (sent 0/5/11, parsed back to
0/2/3), but **policy 1 sends NwMode 1, which the response parser does not recognise and
maps to -1.** The set and get value sets overlap but are not identical. A live capture
should therefore watch specifically for whether `AT*BAND=1` returns `OK` or an error/CME,
and whether the frontend still reports success despite an unrecognised readback. This is a
concrete falsifiable question — but it cannot be answered without an observer.

## 2. `/tmp/atcmd` protocol, reverified

From [analysis/atcmd-ipc.json](../analysis/atcmd-ipc.json):

- transport: `AF_UNIX`, `SOCK_STREAM`; `mobile` connects to a 110-byte `sockaddr_un` for
  `/tmp/atcmd`.
- request: ASCII AT command, literal `0x0d` (CR) appended, no length prefix; `write()`
  must return the full `strlen`.
- response: raw stream reads, line-oriented; confirmed final tokens `OK`, `ERROR`,
  `+CME ERROR`, `+CMS ERROR`, with numeric CME/CMS mapped to internal codes.
- distinct from `/tmp/mobile_msg_server.sock`, which is an `AF_UNIX`/`SOCK_DGRAM` event
  channel — must not be confused with the AT stream.

Unresolved (static): the atcmdsrv-side per-client socket name selection; unsolicited
result-code routing; and **which process actually serves `/tmp/atcmd` in the running
system**. atcmdsrv is the supported candidate, but `libmarvellril.so`/`rild` also
reference `/tmp/atcmd` and `/tmp/atcmdni`, and this was never confirmed live. That
ambiguity is itself an argument for observing rather than assuming.

## 3. The host-side reality check

The management link is Wi-Fi/IP. `/tmp/atcmd` is an `AF_UNIX` socket inside the router's
Linux. Therefore:

- **tcpdump / Wireshark on the PC, browser DevTools, HTTP capture cannot see it.** AF_UNIX
  payloads never traverse the network stack. This is not a tooling gap that better filters
  would fix; it is a layering fact.
- `/proc/net/unix`, `ss -x`, netstat-style listings could establish socket *existence and
  ownership*, but not *payload*. And all of them require device-side execution we do not
  have (see §4).

**Metadata visibility ≠ payload visibility.** Nothing reachable from the host observes the
AT bytes.

## 4. Currently available device-side access: none

Establishing what we legitimately have, without exploiting anything:

- **No shell, telnet, SSH, or debug console.** A firmware-strings and analysis search
  finds **no `telnet`, `dropbear`, `utelnetd`, or `sshd`** anywhere. There is no dormant
  network login service to authorize into.
- The stock web UI offers **no device-side command execution** and no raw log export that
  contains AT traffic (`log:2` builds `/cache/savelog.tar.gz` from system/config/network
  logs — not the AT socket).
- The only paths that would *yield* execution are all out of scope for this phase and/or
  invasive: creating/enabling `/misc/m7000_debug.sh` (a persistent factory-storage hook),
  USB ADB (only present in early-boot production/ramdump modes, i.e. Fastboot-class access),
  UART, and CATStudio. The task forbids all of these, and independently they are not
  "passive."

We therefore have **no authorized device-side observation facility at all.** That fact is
the finding, not a problem to route around by manufacturing access.

### Why the two "stock" facilities do not rescue this

`log:4` is the closest thing to a supported diagnostic tap, and it still fails on every
axis that matters:

1. **Wrong layer.** mdLog / CATStudio capture the Marvell CP *diagnostic* stream
   (DIAG over the CP path), not the AP-side AF_UNIX `/tmp/atcmd` AT socket between `mobile`
   and its AT server. The `AT*BAND=<N>` bytes we want live above the diag layer.
2. **Non-functional as shipped.** `rpmServer` references `/usr/bin/start_mdlog`,
   `/usr/bin/stop_mdlog`, and `pgrep diag_mdlog`, but those helpers and `diag_mdlog` are
   **not present in the SquashFS** ([analysis/debug-hook.md](../analysis/debug-hook.md)).
   The toggle expects a dynamically supplied or persistent component we would have to
   introduce — which is itself out of scope.
3. **State-changing and coupled to disabled storage.** `log:4` starts/stops collectors;
   its useful output path is coupled to SD-card storage that the M7000 reports disabled
   ([docs/soft-capture-002.md](soft-capture-002.md)). CATStudio reboots and can format an
   MTD partition.
4. **Sensitive-data firehose.** Even if it worked, it would produce a raw modem/SIM diag
   stream, not an `AT*BAND`-only view — the opposite of the capture-time minimization this
   work requires.

## 6. Gate decision

**Can we observe `/tmp/atcmd` payload with acceptable risk, using current access? No.**

- Host-side capture is insufficient by construction (AF_UNIX is invisible to IP).
- The device-side access that *would* work (tracefs/ftrace, or at worst ptrace) requires a
  shell and root we do not have and are not authorized to manufacture this phase.
- The only stock diagnostic facilities are the wrong layer, non-functional as shipped,
  state-changing/destructive, and sensitive-data-heavy.

Per the task, a clean negative is the correct outcome here, and no RAT write was performed.

## 7. Safest next observation design (for a future, separately authorized phase)

If and only if a legitimate, authorized device-side execution channel is later established
(the access question is separate and is **not** settled by this note), the least-invasive
technically-sound design would be, in order:

1. **Tier 1 — transient kernel tracing that watches the existing socket without touching
   endpoints or bytes.** Attach a kprobe/tracepoint to the `unix_stream_sendmsg` /
   `unix_stream_recvmsg` path (or the relevant `write`/`read` for the `mobile` FD bound to
   `/tmp/atcmd`), filtered in-kernel to records whose payload begins `AT*BAND`. Emit only:
   timestamp, direction, the `AT*BAND=<mode>` verb+value, and the final result class.
   Never persist the general AT stream. Enable for the single transition window, then
   disable; nothing persistent, no endpoint modified, no byte inserted.
2. **Tier 2 — `strace -p`/ptrace on the confirmed server (or `mobile`)** only if kernel
   tracing is unavailable. This is **not** passive: ptrace stops and resumes threads and
   perturbs timing. It would need its own explicit authorization, an exact syscall/FD
   filter (`trace=write,read` on the `/tmp/atcmd` FD), and an estimate of perturbation
   before any attach. Do not attach automatically.
3. **Never Tier 3.** A socat/socket-replacement/LD_PRELOAD/binary-patch "transparent proxy"
   *becomes* the command path and is interposition, not observation. Excluded regardless of
   authorization for this line of work.

Correlation would be the same shared-clock method used in validation 003: the browser
observer supplies external `T0` (the `wan:1` submission), and the internal tracer supplies
the `AT*BAND` event; align on a relative clock.

## 8. Sensitive-data handling

No live capture occurred, so nothing was persisted. The design above filters to `AT*BAND`
at capture time and never retains a general AT transcript, precisely because a raw AT
stream can carry IMSI/ICCID/IMEI/MSISDN/operator/APN/SMS/SIM-record data. Any future raw
trace stays outside the repo, gitignored, and is discarded once sanitized evidence is
derived.

## 9. Evidence boundary

- **Confirmed (static, this session):** the AP-side `AT*BAND` mapping (1→`AT*BAND=1`,
  3→`AT*BAND=11`), the `/tmp/atcmd` protocol shape, the absence of any network shell in the
  firmware, and the non-viability of the stock diagnostic facilities for this purpose.
- **Not established, and not attempted:** that `AT*BAND=1`/`AT*BAND=11` physically
  traverse `/tmp/atcmd` on hardware. That remains static inference.
- **Still static below the AT boundary regardless:** translation into CI, `/dev/msocket`,
  the CP dispatcher, handler `0x068afdf0`, and `L1CSetRat`.

## 10. Recommendation

The `/tmp/atcmd` boundary cannot be closed on hardware with the access we have, and it
should not be forced. The blocking question is not a capture technique — Tier 1 kernel
tracing is a sound design — but **legitimate device-side execution**, which is a separate
authorization with its own risk profile (it necessarily involves one of the currently
out-of-scope access paths). That decision belongs to the operator. Until it is made, the
AT-command boundary stays static inference, and the `/dev/msocket` / CI phase — which sits
one layer deeper still — is not reachable and must not be started.
