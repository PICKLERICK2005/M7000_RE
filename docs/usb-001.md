# USB Capture 001: Passive Enumeration

Date: 2026-08-15

## Scope

The TP-Link M7000(EU) V3.20 running `3.0.2 Build 241129 Rel.3n` was enumerated
passively on a Windows host through its USB-C connector. The capture used normal
power states only. No web login, AT command, serial-port access, USB payload,
vendor control transfer, driver change, diagnostic tool, special boot mode, or
write operation was performed.

## Power-state comparison

| State | Observation |
| --- | --- |
| USB disconnected | No baseline COM or modem-class device |
| USB connected while off | Brief all-LED illumination; sequential `2ECC:3001` and `2ECC:4E11` vendor-specific identities; neither remains present |
| Powered on with USB connected | Normal boot completed, followed later by enumeration of one USB composite/RNDIS function |

The repeat capture identified the two USB personalities:

1. `2ECC:3001`, product `NEZHAS`, revision `0000`, class `FF/FF/FF`, visible for
   approximately 1.7 seconds.
2. `2ECC:4E11`, product `Openwrt`, revision `0321`, class `FF/42/03`, visible for
   approximately 2.8 seconds.

Neither bound a Windows driver or service. They disappeared automatically before
charging mode settled. This is not yet evidence of a callable bootloader,
recovery, or download interface.

## Powered-on enumeration

The powered-on router appeared as:

- VID:PID `3625:0006`, revision `0318`
- manufacturer/product strings `Quectel` / `M7000`
- USB 2.1 descriptors connected at High-Speed 480 Mbit/s
- one configuration containing two associated interfaces
- USB composite parent using the Windows `usbccgp` driver
- interface 0: RNDIS control `E0/01/03`, interrupt IN endpoint `0x82`
- interface 1: CDC data `0A/00/00`, bulk IN `0x81` and bulk OUT `0x01`
- bus-reported function description `RNDIS`
- Microsoft `usbrndis6` driver through `wceisvista.inf`

Windows exposed the child as **Remote NDIS based Internet Sharing Device**. It
reported a 426 Mbps link rate and MTU 1500. DHCP automatically configured an
IPv4 address on `192.168.0.0/24` with gateway `192.168.0.1`. No application
traffic was deliberately generated.

The USB serial was device-unique and was not committed. USBTreeView reports that
the device advertises SuperSpeed capability but negotiated High-Speed here. The
RNDIS link rate is not a USB speed or throughput measurement.

## Classification

Confirmed observation: normal stock powered-on USB operation exposes an RNDIS
network path to the same `192.168.0.0/24` router network used by Wi-Fi.

Negative observation: no COM/serial, modem, mass-storage, or additional
vendor-specific child appeared during the powered-on window. The two
vendor-specific devices belong only to the powered-off connection transition.

Inference: TP-Link exposes a host networking function in normal operation while
not exposing generic Quectel serial/diagnostic interfaces through the stable USB
configuration. The exact firmware contains `ASRMicro`, `Openwrt`, `ASRF001`,
`mv_udc`, endpoint, and charger-state strings in the same binary, correlating the
second transient with shipped firmware code. Its role remains unproven.

## Recommended next experiment

Research both transient identities and their exact firmware code paths offline
before installing a driver or sending traffic. A further passive host trace may
try to retain their full descriptors. The stable RNDIS path can be characterized
separately under its own narrow allowlist.
